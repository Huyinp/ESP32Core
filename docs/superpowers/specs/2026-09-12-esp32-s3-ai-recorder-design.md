# ESP32-S3 AI 录音终端设计规格

## 1. 目标

基于 Waveshare ESP32-S3-Touch-AMOLED-1.8 V2 开发板制作个人使用的 AI 录音产品原型，验证以下闭环：

1. 不依赖手机即可一键开始和停止录音。
2. 完整录音可靠保存到 microSD，断电或 BLE 断连不丢失已落盘内容。
3. 微信小程序在前台连接设备后自动同步待上传录音。
4. 后端调用火山引擎语音识别和豆包大模型，生成转写、摘要、关键结论和待办。
5. 用户可在微信小程序中播放、管理录音，并针对单条录音追问。

当前阶段使用完整开发板验证功能和体验，不追求录音豆尺寸，也不设计定制 PCB。

## 2. 已确认的硬件与软件基线

- 硬件版本：ESP32-S3-Touch-AMOLED-1.8 V2。
- SoC：ESP32-S3R8，双核 240 MHz、8 MB PSRAM、16 MB Flash。
- 显示与触控：CO5300 QSPI AMOLED、CST820 I2C 触控，368 × 448。
- 音频：ES8311、板载模拟麦克风和扬声器。
- 存储：microSD。
- 电源：AXP2101 和 3.7 V 锂电池接口。
- 其他板载资源：PCF85063 RTC、QMI8658 IMU、PWR 与 BOOT 按键。
- 固件框架：`D:\DevTool\Espressif\frameworks\esp-idf-v5.5.4`。
- 手机端：微信小程序，不开发 Android 原生应用。
- AI 服务：火山引擎语音识别和豆包大模型。
- 网络：首版设备只通过 BLE 与小程序通信；设备 Wi-Fi 留作后续能力。

不得混用 V1 的 SH8601、FT3168 驱动、引脚定义或 Arduino 示例。

## 3. 产品范围

### 3.1 两种录音模式

**随手记**用于短录音。设备始终落盘；小程序处于前台且 BLE 可用时，同时传输实时音频并显示转写。实时链路跟不上时，自动退化为录后同步，不影响本地文件。

**会议**用于长录音。录制期间优先写入 microSD，只向小程序发送状态；停止后再自动断点同步完整录音。

模式由设备触屏首页显式选择，不根据最终时长猜测。

### 3.2 设备交互

- PWR 长按：开机或关机。
- 开机后 PWR 短按：开始或停止录音。
- 开始和停止均提供屏幕动画与提示音。
- 录音页显示模式、录音时长、电量、存储余量、BLE 和同步状态。
- 设备端不提供复杂文件管理；录音管理集中在小程序。
- 手机不在附近、小程序退出或 BLE 断开均不得中断本地录音。

### 3.3 微信小程序 MVP

- BLE 配对、连接与设备状态显示。
- 打开小程序后自动发现并续传待同步录音。
- 设备当前录音状态与同步进度。
- 录音列表、标题修改、播放和删除。
- 转写全文、摘要、关键结论和待办事项。
- 汇总待办页，可手动标记完成。
- 针对单条录音进行问答。

首版不做多用户协作、分享、会员、复杂标签、跨设备同步和设备 OTA。

## 4. 总体架构与数据流

系统由设备固件、微信小程序、轻量后端、对象存储、数据库及第三方 AI 服务组成。

```text
ES8311 麦克风
      ↓ I2S
ESP32-S3 ──写入──> microSD（完整事实来源）
      │
      └──BLE GATT──> 微信小程序临时文件
                         │
                         └──HTTPS 分片上传──> 后端 ──> 对象存储
                                                   │
                                                   ├──> 火山 ASR
                                                   └──> 豆包摘要/问答
                                                            │
微信小程序 <──────────── 查询状态与结果 ────────────────┘
```

microSD 中的完整录音是设备侧事实来源。BLE 实时传输是可丢弃的旁路；任何实时传输拥塞都不得反压 I2S 采集或 SD 写入。

小程序的“默认自动上传”准确含义是：小程序位于前台并成功连接设备后自动同步。退出或进入后台后不承诺持续 BLE 传输；恢复前台后自动断点续传。未来启用设备 Wi-Fi 后，才支持无小程序在场的上传。

## 5. 固件设计

### 5.1 组件边界

- `board`：V2 BSP 及 CO5300、CST820、ES8311、microSD、AXP2101、RTC、IMU、按键初始化。
- `recorder`：I2S 采集、缓冲、编码、文件写入和录音状态机。
- `storage`：文件索引、元数据、临时文件恢复、空间策略。
- `transfer`：BLE 服务、目录同步、分块传输、校验和断点续传。
- `ui`：LVGL 页面、触控、按键事件、状态展示。

组件通过显式消息和状态接口通信。BLE 与 UI 不直接操作 I2S 或录音文件写入器。

### 5.2 状态机

```text
待机 → 准备 → 录音中 → 收尾保存 → 等待同步 → 同步中 → 已同步
                    ↘ 异常恢复
```

不允许同时开始两条录音。停止请求必须先停止采集、排空缓冲、刷新文件并提交元数据，然后才报告保存成功。

### 5.3 文件可靠性

- 开始时创建临时文件和最小元数据。
- 按固定数据块持续写入并周期性刷新。
- 正常停止后补齐容器信息，再原子重命名为正式文件。
- 启动时扫描临时文件，根据已写数据长度恢复可播放文件。
- 正式文件名包含 RTC 时间和不可重复录音 ID；RTC 无效时使用持久启动计数器和序号。
- “已同步”只表示云端确认完整接收，不自动删除设备原文件。
- 用户删除录音或后续容量策略是唯一清理入口。

### 5.4 音频格式

- 采集基线：16 kHz、16-bit、有符号 PCM、单声道。
- 里程碑 1 使用 PCM/WAV 验证 ES8311 收音、稳定性和恢复逻辑。
- 后续目标格式：Ogg/Opus，24 kbps，预计约 10.8 MB/小时。
- Opus 成为默认格式前，必须实测 CPU、内存、功耗、音质、SD 写入和 BLE 同步耗时。
- PCM/WAV 作为诊断选项保留，不作为长期 BLE 同步默认格式。
- 首版不在 ESP32 上做降噪、说话人分离或语音识别。

### 5.5 任务优先级

从高到低为 I2S 采集、SD 写入、文件恢复元数据、BLE 传输、UI 动画。实时 BLE 消费独立缓冲；缓冲不足时丢弃实时旁路数据，并向小程序报告退化状态，完整录音仍保存在 SD。

## 6. BLE 协议

设备提供一个自定义 GATT Service，包含以下特征：

- 控制特征：开始/停止、模式、文件列表、同步请求、暂停和取消。
- 状态特征：录音状态、时长、电量、SD 余量、错误码和同步进度。
- 数据特征：音频块通知。
- 确认特征：小程序提交已持久保存的连续字节偏移。

每个数据块包含协议版本、消息类型、录音 ID、文件偏移、数据长度、序号和 CRC。协议使用小端二进制编码，并在规格实现阶段固定字段长度。

同步流程：

1. 小程序读取设备文件索引。
2. 小程序把设备索引与后端状态对比，选出未同步或未完成文件。
3. 小程序提供已确认连续偏移，设备从该位置继续。
4. 设备根据协商 MTU 和发送窗口连续通知数据。
5. 小程序先把数据持久写入临时文件，校验后才确认偏移。
6. 完整文件通过 HTTPS 上传；后端校验文件哈希后确认完成。
7. 小程序通知设备更新“已同步”标志。

实现不得假定固定 MTU 或固定吞吐率。断连、乱序、重复块和 CRC 错误都必须可恢复，重复提交必须幂等。

录音数据通过 BLE Secure Connections 保护，开发板显示一次性配对码。配对与加密能力需要在 Android 微信实机上优先验证；若微信 BLE API 无法稳定触发安全配对，需在进入正式音频传输前补充应用层会话加密设计，不能静默降级为无保护音频传输。

## 7. 微信小程序设计

### 7.1 页面结构

- **录音页**：设备连接卡片、当前录音、待同步数量、最近录音。
- **待办页**：聚合 AI 生成的待办，支持完成状态。
- **设备页**：配对、电量、存储、同步策略、固件信息。
- **录音详情页**：播放器、摘要、结论、待办、全文和追问。

设备端页面保持极简，只承载模式选择和即时状态。

### 7.2 小程序本地职责

- 管理 BLE 连接与前后台生命周期。
- 将收到的音频块持久写入临时文件。
- 保存每个文件的连续确认偏移和云端上传进度。
- 恢复前台后重新读取设备索引并自动续传。
- 所有删除、重命名和状态更新请求采用幂等接口。

小程序不保存火山引擎或豆包密钥，也不直接调用第三方 AI 服务。

## 8. 后端设计

首版使用一个 Python FastAPI 单体服务，不拆微服务：

- 微信登录与单用户设备绑定。
- 音频分片上传、合并、哈希验证。
- 录音元数据和处理状态。
- 火山引擎流式及录音文件识别适配。
- 豆包摘要、待办提取和单录音问答。
- 一个基于数据库任务表的后台工作进程。

音频保存在对象存储，结构化数据初期使用 SQLite。只有出现多实例部署或实际并发需求时才迁移 PostgreSQL。首版不引入 Redis、消息队列或微服务。

API 密钥仅通过后端运行环境注入，不写入仓库、小程序包或固件。后端对小程序暴露 HTTPS 接口，并校验微信身份及录音所有权。

### 8.1 核心数据实体

- `Device`：设备 ID、所有者、配对状态、固件版本。
- `Recording`：录音 ID、模式、开始/结束时间、时长、格式、大小、哈希、处理状态。
- `Transcript`：完整文本、分段时间戳、语言及识别服务元数据。
- `Summary`：摘要、关键结论、关键词及模型版本。
- `ActionItem`：内容、完成状态、来源录音。
- `Job`：上传校验、转写、摘要任务的状态、重试次数和最后错误。

### 8.2 AI 输出约束

摘要固定生成以下结构：

- 标题建议
- 一段简要摘要
- 关键结论列表
- 待办事项列表；无法确定责任人或截止时间时保持为空，不臆造
- 关键词

会议与随手记使用不同提示模板。会议侧重决定、分歧和行动项；随手记侧重核心想法、可执行下一步和关键词。

## 9. 错误处理与隐私

- SD 缺失或空间不足：拒绝开始并明确显示原因。
- BLE 断开或小程序退出：本地继续录音，保留确认偏移。
- 小程序上传失败：保留临时文件和上传进度。
- ASR 失败：保留音频并仅重试 ASR。
- 摘要失败：保留转写并仅重试摘要。
- 文件校验失败：重传损坏范围，不重传完整文件。
- 意外掉电：下次启动修复临时文件，不覆盖既有录音。
- 删除录音：删除对象音频、转写、摘要、待办及关联任务；设备原文件由小程序在云端删除成功后另行请求删除。

原始音频默认长期保留，不做未经用户确认的自动过期。日志不得记录音频正文、完整转写或密钥。

## 10. 验证标准

### 10.1 里程碑 1：硬件录音基线

- PWR 短按可开始和停止录音，长按关机行为不冲突。
- 连续录制 2 小时无采集溢出或文件损坏。
- 录音期间强制掉电，重启后可恢复已落盘部分。
- 文件可在常用播放器中播放，时长与设备计时误差在可解释范围内。
- 实测板载麦克风在随身近讲和桌面会议距离下的可懂度及噪声。

### 10.2 里程碑 2：BLE 可靠同步

- 小程序可连接、查看状态和文件索引。
- 多次随机断连后可自动续传。
- 最终文件 SHA-256 与 SD 原文件一致。
- 重复同步不会创建重复录音。
- 前后台切换不会破坏设备本地录音。

### 10.3 里程碑 3：云端闭环

- 上传后可获得转写、摘要、结论和待办。
- 每个异步阶段有明确状态和独立重试路径。
- 固件和小程序发布包中不存在第三方服务密钥。
- 删除流程覆盖结构化记录和对象存储文件。

完成里程碑 1 至 3 定义为基础 MVP。里程碑 4 的随手记实时转写和里程碑 5 的 Opus 优化属于后续增强，不阻塞基础 MVP 验收。

### 10.4 后续里程碑

- **里程碑 4**：随手记前台实时传输和转写；BLE 跟不上时可靠退化。
- **里程碑 5**：Opus 实测达标后设为默认；完成追问、待办及错误体验完善。

## 11. 测试策略

- 固件：录音状态机、文件恢复、索引和 BLE 编解码单元测试。
- 协议：使用主机端模拟器覆盖断连、重复、乱序、CRC 错误和续传。
- 后端：上传幂等性、状态迁移、AI 适配器、鉴权和删除 API 测试。
- 小程序：状态管理与协议解析测试，加 Android 微信真机生命周期测试。
- V2 实板：长录音、强制掉电、SD 满、BLE 弱信号、反复前后台切换和低电量测试。

任何只在模拟器通过、未在 ESP32-S3-Touch-AMOLED-1.8 V2 实板验证的硬件结论，都不得标记为已验收。

## 12. 明确延后事项

- 设备 Wi-Fi 自动上传。
- 定制小型 PCB、双麦克风阵列、充电仓和防水结构。
- 设备端降噪、VAD、ASR 或说话人分离。
- iOS/Android 原生 App。
- 多用户、组织协作、分享、会员和计费。
- OTA 与量产安全体系。
